1. O que é DevOps?

DevOps = Desenvolvimento + Operações. É uma abordagem que aproxima quem constrói o software (dev) de quem coloca em produção e mantém (ops), usando cultura, processos, ferramentas e muita automação para entregar software de forma mais rápida, segura e confiável.

O problema dos "silos"

Antes do DevOps, cada equipe trabalhava isolada, com objetivos, processos, ferramentas e indicadores diferentes. O resultado clássico era a disputa de culpas:

👨‍💻 Dev: "Na minha máquina funciona."
🖥️ Operações: "Em produção não funciona."
🧪 QA: "Nos testes funcionava."
🔒 Segurança: "Essa configuração não pode ir para produção."

DevOps ataca a causa: o processo, não as pessoas. A responsabilidade pelo resultado passa a ser compartilhada por todo o time.

DevOps NÃO é...

❌ só Docker ❌ só Kubernetes ❌ só CI/CD ❌ só Cloud ❌ um cargo ❌ uma ferramenta

DevOps é uma mudança de mentalidade: começa com a pergunta "qual problema queremos resolver?" e só depois escolhe processo → automação → ferramenta → métrica → melhoria.

O ciclo contínuo

PLAN → CODE → BUILD → TEST → RELEASE → DEPLOY → OPERATE → MONITOR → FEEDBACK → (volta ao PLAN). O software nunca está "terminado" — está em evolução constante.

Quem faz o quê

ÁreaResponsabilidadeExemplos de ferramentas
DEVescrever código, corrigir bugs, evoluir funcionalidadesGit, GitHub, VS Code, frameworks
QAgarantir qualidade: testes funcionais, regressão, desempenhoJest, PHPUnit, JUnit
OPSservidores, redes, banco, cloud, disponibilidade, monitoramentoDocker, Kubernetes, Ansible, Terraform
SECURITYsegurança presente desde o início (DevSecOps / Security by Design)SonarQube, Trivy

2. Git — Controle de Versão

Git é um sistema de controle de versão distribuído: cada desenvolvedor tem uma cópia local completa do repositório e do histórico. Isso permite trabalhar offline e colaborar com segurança.

Git ≠ GitHub. Git é a ferramenta; GitHub (ou GitLab) é a plataforma que hospeda o repositório e adiciona colaboração (Pull Requests, Code Review, Issues, CI/CD).

As três áreas do Git

ÁreaO que éComando
Working Directorya pasta onde você trabalha nos arquivosgit status
Staging Areaárea de preparação do próximo commitgit add arquivo / git add .
Repositoryhistórico oficial versionadogit commit -m "mensagem"

O remoto (GitHub) é sincronizado com git push (envia) e git pull (recebe). Para baixar um projeto novo: git clone url.

Commit = checkpoint

Cada commit é um "ponto salvo" do projeto. Bons commits têm mensagens claras e objetivas:

  • ❌ git commit -m "alterações"
  • ✅ git commit -m "Corrige validação de senha no login"

Branches, merge e conflitos

Branch é uma linha independente de desenvolvimento. Você cria uma branch para uma funcionalidade sem mexer no código principal:

git switch -c feature/login   # cria e muda para a nova branch

Quando termina, integra de volta com git merge feature/login. Se duas pessoas editaram a mesma linha, ocorre um merge conflict — o Git pausa e pede para você escolher a versão correta.

Pull Request (PR)

Fluxo colaborativo: feature → push → Pull Request → Code Review → aprovação → merge → main. O PR permite revisar o código, comentar e rodar testes automáticos antes de integrar.

Comandos essenciais

git status      # situação dos arquivos
git add .       # prepara alterações
git commit -m "msg"
git log         # histórico
git switch -c feature/x
git merge feature/x
git push / git pull / git clone url

3. Git Flow — Organizando o trabalho em equipe

Git Flow é uma estratégia de branches (não uma funcionalidade obrigatória do Git). Cada tipo de branch tem uma finalidade clara, separando desenvolvimento, releases e correções urgentes.

BranchFinalidade
maincódigo estável, pronto para produção. Nunca desenvolva direto nela.
developlinha de integração: onde as features prontas se juntam.
feature/*novas funcionalidades, partindo de develop. Ex.: feature/login
release/*preparação de uma versão: testes finais e ajustes, sem parar o desenvolvimento. Ex.: release/1.2.0
hotfix/*correção urgente de bug em produção, partindo de main.

Os três fluxos

Feature: develop → feature/login → commits → push → PR → review → merge em develop

Release: develop → release/1.2.0 → testes finais → merge em main e em develop → tag v1.2.0

Hotfix: main → hotfix/corrige-login → correção + testes → merge em main e em develop → nova tag

💡 Tags marcam versões específicas (v1.0.0, v1.2.0) para rastrear exatamente qual código foi publicado.

Erros comuns a evitar

  • Trabalhar diretamente em main
  • Branches gigantes que duram semanas / commits sem significado
  • Merge sem revisão e sem testes
  • Colocar senhas ou tokens no repositório (nunca!)

4. Docker — Containerização

Usuários reclamavam: "na minha máquina funciona". Containers resolvem isso empacotando a aplicação com todas as dependências num ambiente isolado, leve e reproduzível. Uma imagem pode ser executada em qualquer máquina com Docker e se comporta igual.

Container × Máquina Virtual

Uma VM carrega um sistema operacional inteiro; um container compartilha o kernel do host, por isso inicia em segundos e usa poucos MB. Containers são descartáveis: você destrói e recria sem apego.

Conceitos principais

ConceitoExplicação
Imagem"receita" imutável da aplicação (código + dependências + config).
Containerinstância em execução de uma imagem.
Docker EngineDocker Client (você) + Docker Daemon (executa tudo).
Registryservidor que armazena imagens (Docker Hub = público; ECR/GHCR = privados).

O fluxo de trabalho

Código → Dockerfile → docker build → Imagem → docker run → Container → docker push → Registry.

Comandos do dia a dia

docker --version && docker run hello-world   # testa a instalação
docker images                                # lista imagens
docker ps / docker ps -a                     # contêineres ativos / todos
docker run -d --name web -p 8080:80 nginx    # sobe o Nginx na porta 8080
docker logs web                              # logs
docker stop web && docker rm web             # para e remove

5. Dockerfile — Receita da imagem

O Dockerfile é um arquivo de texto com instruções para construir a imagem. Cada instrução gera uma camada (layer). A ordem importa!

FROM node:22-alpine      # 1. imagem base
WORKDIR /app             # 2. diretório de trabalho dentro da imagem
COPY package*.json ./    # 3. copia só o necessário p/ cache
RUN npm install          # 4. instala dependências (no BUILD)
COPY . .                 # 5. copia o restante do código
ENV PORT=3000            # 6. variável de ambiente
EXPOSE 3000              # 7. documenta a porta
CMD ["npm", "start"]       # 8. comando padrão ao iniciar
InstruçãoO que faz
FROMdefine a imagem base (ex.: node:22, python:3.12-slim, nginx:alpine)
WORKDIRdiretório de trabalho; comandos seguintes rodam ali (criado se não existir)
COPYcopia arquivos do contexto de build para dentro da imagem
RUNexecuta comandos durante o build (instalar deps, etc.)
EXPOSEdocumenta a porta usada — não publica! Publicar é com -p
CMDcomando padrão, facilmente substituível no docker run
ENTRYPOINTexecutável principal da imagem; combinável com CMD (args padrão)
ENVvariável de ambiente embutida na imagem
⚠️ RUN acontece no build; CMD acontece na execução do container. EXPOSE 3000 sozinho não abre a porta — precisa de docker run -p 8080:3000 app.

Build e tag

docker build -t minha-app:1.0 .
docker run -d --name app -p 3000:3000 minha-app:1.0
docker tag minha-app:1.0 usuario/minha-app:1.0
docker push usuario/minha-app:1.0

Prefira tags explícitas (:1.0) em vez de depender de latest em produção. Variáveis de app como PORT, DB_HOST são passadas com -e ou --env-file — nunca senhas direto no Dockerfile.

6. Volumes, Redes e Docker Compose

Por que persistência?

Containers são descartáveis: se você remover um container, os dados gravados dentro dele se perdem. Um banco de dados não pode funcionar assim.

Volume DockerBind Mount
Quem gerenciao próprio Dockervocê, via caminho do host
Uso idealdados persistentes / produçãocódigo-fonte em desenvolvimento
Exemplo-v dados_mysql:/var/lib/mysql-v $(pwd):/app

Com bind mount, o que você edita no notebook aparece na hora dentro do container — perfeito para desenvolvimento com hot reload.

Redes — como contêineres conversam

Contêineres na mesma rede Docker se comunicam pelo nome do serviço (DNS interno), não por IP e nem por localhost:

# dentro da API, o banco é encontrado por:
DB_HOST=database

Docker Compose — vários serviços, um arquivo

Em vez de subir cada container na mão, você declara tudo em um docker-compose.yml:

services:
  api:
    build: .
    ports: ["8080:8080"]
    environment:
      DB_HOST: database
    depends_on:
      - database
  database:
    image: mysql:8
    volumes:
      - mysql_data:/var/lib/mysql
volumes:
  mysql_data:
docker compose up -d          # sobe tudo em background
docker compose ps             # lista serviços
docker compose logs -f        # acompanha logs
docker compose down           # para e remove (add -v p/ apagar volumes)
docker compose up -d --build  # reconstrói e sobe
💡 depends_on só controla a ordem em que os serviços sobem — não garante que o banco esteja pronto para conexões. Por isso existem healthchecks e retry.

7. Boas Práticas e Multi-stage Builds

Checklist de uma boa imagem

  • ✅ Imagem base adequada e com versão específica (node:22-alpine)
  • ✅ Sem segredos na imagem (nada de ENV DB_PASSWORD=... ou COPY .env .)
  • ✅ .dockerignore configurado (node_modules, .git, .env, dist, logs)
  • ✅ Cache aproveitado: dependências antes do código
  • ✅ Usuário não-root quando possível
  • ✅ Multi-stage build quando aplicável

Cache do Docker

O Docker reconstrói camada por camada e reutiliza o que não mudou. A ordem das instruções define o que é cacheado:

# ❌ ruim: mudou o código, reinstala tudo
COPY . .
RUN npm install

# ✅ bom: só o código mudou → npm install fica em cache
COPY package*.json ./
RUN npm ci
COPY . .

Multi-stage build

Problema: para construir uma aplicação Vue/React você precisa de Node, npm e ferramentas pesadas — mas em produção só precisa do HTML/JS/CSS gerado. Multi-stage separa as fases com múltiplos FROM:

# Stage 1 — build (pesado)
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2 — produção (leve)
FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

Resultado: a imagem final tem somente Nginx + dist/. Antes × depois:

Sem multi-stageCom multi-stage
Node + npm + Vite + node_modules + código-fonte + distNginx + dist/

Benefícios: menos espaço em disco, downloads/deploy mais rápidos, menor superfície de ataque e menos componentes para atualizar.

8. CI/CD — Integração e Entrega Contínua

Deploy manual é lento, repetitivo e cheio de erros. CI/CD automatiza essa esteira:

ConceitoO que fazDiferença-chave
CI — Continuous Integrationa cada git push, integra o código e valida: build + testes + lintdetecta problemas cedo
Continuous Deliverydeixa a aplicação sempre pronta para implantardeploy em produção depende de aprovação humana
Continuous Deploymentapós passar nos critérios, implanta sozinhozero intervenção humana no deploy

Pipeline

É a sequência automatizada de etapas:

Checkout → Dependências → Build → Testes → Análise → Empacotar → Deploy

Se qualquer etapa falha, a equipe recebe feedback rápido e corrige antes de chegar ao usuário. Uma pipeline não serve só para entregar — ela mede a qualidade de cada alteração.

🤖 Automatizar não é "fazer sem pessoas": é transformar tarefas repetitivas e verificáveis (instalar deps, testar, gerar build, publicar imagem, deploy) em processos executados por ferramentas.

9. GitHub Actions × GitLab CI

Regra mental: o evento inicia a automação → o pipeline organiza o trabalho → o runner executa.

Unidade de trabalhojobjob

Comandosrun:script:

YAML na prática

YAML usa indentação com espaços (nunca TAB), pares chave: valor e listas com -. Um erro de indentação quebra o pipeline.

GitHub Actions:

name: Primeiro Pipeline
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test

GitLab CI (equivalente):

stages:
  - test
  - build

test_app:
  stage: test
  image: node:22
  script:
    - npm ci
    - npm test

Conceitos importantes

  • Events: gatilhos — push, Pull Request/Merge Request, agendamento, execução manual.
  • Jobs: unidades de trabalho com seus próprios comandos; podem rodar em ambientes diferentes e depender de outros jobs.
  • Stages: fases do pipeline (test → build → deploy) que definem a ordem.
  • Runner: a máquina que executa os comandos — pode ser hospedado pelo GitHub/GitLab ou self-hosted na sua infraestrutura.

Esteira completa

git push → CI (build + testes + lint + security scan) → docker build → push para o Registry → deploy → monitoramento.
